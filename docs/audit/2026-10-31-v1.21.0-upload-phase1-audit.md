# Phase 1 — audit of the uploaded `DT-POS-Enterprise-v1.21.0-source.zip`

Date: 2026-10-31. Source inspected read-only (extracted to a scratch folder; nothing in it was modified or run except the
project's own `tsc`, `vitest` and `vite build`). Evidence labels: **MEASURED** (I ran it), **READ** (I read the code/rules),
**AUTHOR-STATED** (from the project's own docs), **NOT VERIFIED** (could not be tested here).

## 1. What this ZIP is — and what it is not

It is **DT POS Enterprise v1.21.0, the offline Windows edition**, plus its **Firebase-based Super Admin panel** (`superadmin/`).
It is *not* a version of the cloud/SaaS code in the `digitaltarget.digital` repository (v1.70.1), although the two share an ancestor:

| | Uploaded v1.21.0 (offline edition) | `digitaltarget.digital` v1.70.1 (cloud edition) |
|---|---|---|
| Shape | Vite SPA + `react-router-dom`, Electron inside the same repo (`electron/main.cjs`, 2,275 lines) | TanStack Start (server functions), Electron shell in a separate repo (`dtpos-desktop`) |
| Business data | **100 % local.** `offlineNoCloud.ts`: `isCloudConfigured()` is permanently `false`. Data in `DT-POS/data/dtpos.json` (atomic writes) + localStorage | Supabase Postgres, RLS per tenant, offline queue + sync |
| Tenants / Workspace Code | **None.** `tenantId` is `null`; the word "workspace" appears in no source file | Tenant + branch model, Workspace Code |
| Super Admin | Separate static Firebase app: licence keys (HMAC), client registry, devices, billing/invoices, support, admin-password reset | Supabase-based, restaurants/plans/devices; **no "clients" entity** |
| Customer website / Order Taker / Rider / Owner portal | In-POS pages only (`OnlinePortalPage`, `OrderTakerPortalPage`, `RiderAppPage`, `OwnerLoginPage`) working on local data; **no cloud order flow, no APKs** | Exist (customer portal, Order Taker + Rider APK shells, `/owner`), with the sync backend |
| Shared source | 269 of 532 `src/` paths are the same name in both trees; only **64 are byte-identical** | |

Consequence for the brief: the "Windows offline POS → cloud APIs → central SaaS → owner portal → website → APKs" chain is not one
codebase today. The offline edition is the Windows half; the cloud edition holds the rest. **Which one the work continues on is a
decision for you — see §7.**

## 3. The client / restaurant bug from the brief — mechanism found and reproduced

> "I create a client, save it, link it to a restaurant, refresh — the client disappears."

In this codebase a *client* **is** a licence record (`clients/{licence key}`, with `business` = the restaurant); "linking" is registering the
shop's activation code on the Device Map (`MapTab.link`) or editing the licence. There is no separate restaurant entity to link to.

**Mechanism (READ + REPRODUCED).** `superadmin/src/App.tsx` lines 65–115 keep the registry in React state, mirror it to `localStorage`
on every change, and subscribe to Firestore with **"the cloud wins"**: every snapshot replaces the state (`setClients(list)`), clears the
error banner (`setCloudErr(null)`) and resets the "already synced" map. Consequences:

1. **A change whose cloud write fails is silently undone.** The push rejects → a red banner appears → Firestore rolls the local write back and
   re-emits the server list → the snapshot handler replaces the state (change gone), overwrites the localStorage mirror, **and clears the banner**.
   The operator saw "saved", then a refresh shows it missing, with no message left.
2. **An empty or stale first snapshot wipes the screen and the offline mirror.** Snapshot `[]` → state `[]` → the `saveClients` effect writes `[]` to localStorage.

Both are reproduced against the real `<App/>` with a controllable listener: `docs/audit/repro/superadmin-client-vanishes.repro.test.tsx.txt`
(2 tests, pass = the behaviour exists). The project's own 1,517 tests never exercise this loop — they turn every `watch*` function into a no-op.

**Not verified:** *why* the cloud write fails or the snapshot is empty in your live system (rules not published for a new project, signed-out
session, offline, Firebase quota…). I have no access to the Firebase project `dtpos-offline`. The rules in the ZIP (`clients`: any signed-in user may read/write)
would not reject a normal write, so the trigger is probably environmental. **The mechanism is a defect either way**: a failed save must never look saved and must never be erased by a refresh.

**Proposed fix (Phase 3, not applied):** keep unsynced/failed records in a pending set that snapshots merge *around* instead of replacing; ignore
`fromCache`/empty snapshots for deletion; never clear an error while a record is unsaved; mark the row "not saved — retry"; stop mirroring a snapshot over unsynced local data; add the two reproductions as regression tests plus a live check against the real project.

## 6. Roadmap (nothing below is started)

1. **P0, small, safe, independent of the decision** — Super Admin: lockfile (F2), sync-loop fix with regression tests (§3), `qrcode` dependency (F8).
2. **P1** — security: Super Admin roles + audit log + closing `supportMessages` reads (F1, F3).
3. **P2** — decision §7 drives everything else: UI/UX redesign (Phase 2) of the chosen Windows app; full billing test pass (Phase 4) on a real Windows machine with a printer.
4. **P3** — Customer site / APKs / owner portal: continue in the cloud edition (already present); anything added to the offline edition needs a cloud sync layer first.
5. **P4** — QA matrix, security report, release docs.

## 7. Decision needed

- **A (recommended).** Keep the cloud edition as the platform for everything cloud-shaped (it already holds website, APK shells, owner portal, workspace code, sync). Treat v1.21.0 as the *offline edition*: apply P0/P1 to it and its Super Admin, and redesign its UI only if you want it to stay on sale.
- **B.** Make v1.21.0 the Windows POS of the whole ecosystem. That means adding tenants, a Workspace Code and a sync layer to a codebase that has none — a large new subsystem with a risk to the stable offline billing.
- **C.** Work only on v1.21.0 and its Super Admin (Phases 1–4 of the brief); leave the website, APKs and owner portal out.

Whichever you choose, the P0 fixes in §6 apply to the uploaded Super Admin and are independent of it.
