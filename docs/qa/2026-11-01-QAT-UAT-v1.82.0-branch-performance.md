## 2. Findings that change the plan
| # | Finding | Decision |
|---|---|---|
| BF-1 | The client model did not declare `branchId` on transactions, inventory or wastage, though the database stamps it. | Declared (type only). |
| BF-2 | Employees, payroll, suppliers and recipes are **not branch-stamped** on write, so branch-wise staff cost / supplier balances cannot be reported. | **OPEN.** Stamping would also hide a branch manager's new employee from other branches' managers under existing RLS — an isolation decision for the owner (question 5 in the architecture note). Staff are counted from sign-in users meanwhile. |
| BF-3 | `user_branch_access` already exists for multi-branch managers. | A regional-manager role is a template + UI on top of it, not a new mechanism. |
| BF-4 | An all-branch owner login writes unstamped rows. | Shown as "No branch recorded", included in the group, never hidden. |

## 3. NOT EXECUTED
- Real tills / two devices syncing; production data volume (all figures are computed in the browser from the collections held in memory — fine for a handful of branches, the server-side aggregation of Phase 3 is the answer for large chains).
- Phone, tablet, Windows shell; the Modern-style rendering (Classic only was seen).
- A branch-limited user on the real database (the page applies the same helpers as other pages; the RLS check on a branch database is still to be run).
