## 2. Decisions and defects
| # | Finding | Decision |
|---|---|---|
| ED-1 | Each realtime event made every device re-read the whole collection (≈ 0.9 MB of orders, 0.7 MB of customers). | **FIXED** — delta read behind `ENABLE_REALTIME_DELTA_RELOAD`. |
| ED-2 | The rider app wrote the whole order on every GPS fix; each write also rebuilt the order's item rows in the database. | **FIXED** — rationed (15 s and 20 m, 90 s heartbeat, route cap 60). |
| ED-3 | The realtime server's WAL polling is the most expensive statement in the database (2.0 M calls, ≈ 4.9 h), driven in part by `order_items` rewrites that nothing subscribes to. | **OPEN** — drop `order_items` from the publication; needs your approval (`docs/EGRESS.md` §4). |
| ED-4 | D-5 (rider ping replaces the order's whole `data`) still stands. | **OPEN** — needs approval and a confirmed backup. |
| ED-5 | After a dropped websocket the till catches up at the next event, not at the moment it reconnects. Unchanged by this release (it was the same with full reloads). | **NOT CHANGED** — a catch-up on re-subscribe is a possible follow-up. |
| ED-6 | PostgREST returns at most 1,000 rows per request by default; the customers collection has 2,271. Whether this project raised the limit was **not checked**. | **NOT VERIFIED** — check Dashboard → Settings → API → Max rows. |
