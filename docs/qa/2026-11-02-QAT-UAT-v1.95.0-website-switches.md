# QAT and UAT — DT POS Enterprise v1.95.0 (the customer website knows the owner's switches)

Design package build order, **step 3** (customer order site), part 1. Reading the website's code and the live database to see what data the new design could use turned up a fault that comes first.

## 1. What was found
The owner's settings live in `tenant_settings`. The database has **no read policy for an anonymous visitor** on that table (checked against the live policies: anonymous visitors can read only branches, categories, deals and menu items). The customer website reads its settings from the local store, so for a real customer they were always the defaults. Consequences, all confirmed in the code and the live database:
- The **Online ordering** master switch (Settings → Online Ordering, the Online Portal page, and the **Owner app's Website switches added in v1.91.0**) was never seen by the page. The "temporarily closed" screen could only appear on a machine where the owner was signed in. `public_place_order` does not look at the switch either. At the time of checking, one of the three restaurants in the live database had it switched **off**, and nothing stopped a customer from ordering.
- **Delivery**, **Pickup** and **Guest checkout** switches: the page never read them, for anyone.
- The **delivery fee**, **free-delivery threshold**, **minimum order**, **pickup time slots** and the restaurant's phone number, as set by the restaurant, did not reach customers either (they saw the defaults). No restaurant in the live database had set a fee or a minimum yet, so no configured fee or minimum was being skipped so far.

The v1.91.0 Owner-app switches therefore saved the setting but did not change what customers could do. That is corrected here, and the Owner app's wording is now true.

## 2. What was built (no database change)
- **`getPublicStorefront`** — a server function that reads the restaurant's settings row with the server's own key and returns only an **allow-list**: name, public phone, currency symbol, tagline, banner, the four switches, self-pickup, delivery fee, free-delivery threshold, minimum order, pickup slots, the restaurant's coordinates. Nothing else (no staff, PINs, payment accounts, receipt text, tax numbers; the owner's personal WhatsApp number is deliberately left out — the public WhatsApp number comes from the customer-app configuration as before). The last answer is remembered on the device; if the server cannot be reached the page behaves exactly as before.
- **The website honours the switches:**
  - Online ordering off → the existing "temporarily closed" screen, now with the restaurant's name and phone.
  - Delivery off → delivery is not offered; Pickup off → pickup is not offered. The choice screen appears only when both are offered; if only one is, it is chosen for the customer. Pickup is still offered only when the restaurant has enabled Self-Pickup (as always); the Pickup switch can only take it away. If nothing is offered the checkout says so and the button is disabled.
  - Guest checkout off → "This restaurant takes orders from signed-in customers only"; pressing Place Order opens sign-in. A name saved on the device after an earlier order does **not** count as being signed in.
  - The delivery fee, free-delivery threshold, minimum order and pickup slots now apply to real customers.
- **The order submission checks the same rules** before it reaches the database, as a backstop for a stale page or a hand-made request. The restaurant's own staff orders (order taker) are never blocked. If the settings cannot be read, the order is **not** blocked (a failed read must not stop a sale); only a clear "closed" answer blocks.

## 3. Not changed, and why
- **`public_place_order` (the database function) was not modified**, nor was any table, policy or column. The enforcement is in the server function that calls it. A person calling that database function directly with the public key (not through the website) is therefore not stopped by the switches; closing that route needs a database change and your approval.
- **The delivery fee is still not added to the order total by the database**: the function prices the items only. It was that way before; it is not changed here and should be reviewed together with the point above.
- **The new website design (WEB-01…21) is not built yet.** Next: the home page, header, hero, category tiles and item cards on this data. The banner and tagline set in Settings now reach customers, so a hero can use them. **Opening hours, several banners and social links** were planned as a new table needing a database backup and your approval; they can instead be kept as new fields in the existing settings document and served through this same allow-list, **with no schema change and no backup needed**. That is the recommended route; say if you prefer the table.
