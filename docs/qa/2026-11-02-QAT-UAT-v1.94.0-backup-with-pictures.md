# QAT and UAT — DT POS Enterprise v1.94.0 (Backup with pictures)

Master directive #12, part 2. Before building, the other two items of the directive were checked against the offline POS (v1.21.0):

- **KOT designer** — `KitchenReceipt.tsx` (1,270 lines), `ReceiptStyleEditor.tsx` and `AutoKotPrinter.tsx` are **byte-identical** to the offline POS (they came over with the Printing Center). Nothing to port.
- **Backup and restore** — the page differs from the offline one only in cloud wiring. Neither version handles pictures, and in this app that is a real gap (below).

## 1. The gap
The backup file is the restaurant's data as JSON. In this app menu photos, category pictures, logos and banners are uploaded to cloud storage and the data holds **only a link** to each. A backup therefore restores every item **without its picture** whenever the storage is not the same one — a new account, a lost bucket, a handover to another restaurant.

## 2. What was built
- **Export with pictures** (Backup & Restore, new button under Export JSON): each linked picture is fetched and put in the file in place of its link, as a data URL. The file stays ordinary JSON, so any till can restore it and the pictures show. A picture shared by several items is fetched once. A picture that cannot be fetched (not found, network error, not an image, over 4 MB) **stays a link**, is counted, and the toast says how many — the backup still completes.
- **Restore** recognises a backup that carries pictures and asks: *Upload the pictures* (recommended: they go to this restaurant's own storage and the data keeps small links) or *Keep inside the data* (nothing uploaded; the data becomes larger), or Cancel. Identical pictures are uploaded once, three at a time, with progress. A picture whose upload fails stays inside the data (it still shows) and the result says how many. A plain backup, or a till with no cloud storage, restores exactly as before — no question asked.
- **Covered:** category, menu item, inventory item and deal pictures; the receipt, app, website and order-taker logos; the website banner.
- **Not covered, on purpose:** staff photos and documents (personal data in a private bucket) and the older display slideshow images (already inside the data as base64).
- The plain **Export JSON** is unchanged.

## 3. Not changed, and why
- The backup is still `exportData()` — the store's own data. Modules kept outside it (the `module_documents` store) were not part of the backup before and are not now.
- On upload the existing `uploadTenantImage` is used, so tenant paths, buckets and policies stay in one place. It re-encodes a picture as JPEG (already ≤ 800 px), so a restored picture loses a little quality compared with the packed one.
- The same bytes used as a menu picture and as a logo count as two pictures (they go to different buckets).

## 5. NOT EXECUTED
- **A real upload to Supabase storage** — the browser check had no signed-in session, so the upload path ran only to its failure branch; the success branch is tested with a stand-in uploader. The upload function itself is the existing one (unchanged).
- **Fetching pictures from the real storage URLs** — the sandbox cannot reach the project's storage (the proxy answers 403), so whether those public buckets send the cross-origin headers a browser needs was **not verified**. If they do not, the effect is that pictures stay as links and the toast says so; nothing is lost.
- **A large restaurant** (hundreds of pictures): time and memory not measured. Each picture is about 100 KB, so 500 pictures make a file of roughly 50 MB.
- The desktop save dialog (Windows app) for the new button — it uses the same function as the plain export.
