# QAT / UAT — v1.108.0 (6 Nov 2026): sync audit, S-4 / S-5, Super Admin overview, Windows-capable card

## 1. How the sync defects were found
Not by guessing: the live project's last 24 hours of edge, API and database logs, then the bodies of the functions the apps call. Rider and Order Taker made **no** calls in that window, so for those two the evidence is the function bodies and the stored data (60 days), not traffic.

| # | Evidence | Cause | Fix | Check |
|---|---|---|---|---|
| 1 | 35 rejected bill inserts in 9 h (unique bill number per branch); 21 of 333 bills renumbered in 2 days (`originalOrderNumber` stored) | When the server counter does not answer within 1.5 s a till numbers from its own counter, which only rose from its own bills — another till's #5171, already on screen, was invisible to it | the fallback starts above the highest number this device holds for the branch (`highestKnownOrderNumber`); the preview agrees | 5 unit tests; the Day Close test was updated: after a reset the new number sits above a kept "udhaar" bill instead of duplicating it |
| 2 | 3 × `null value in column "loyalty_points"` | a null sent for a NOT NULL column with a default means "store nothing" and is a permanent error; and a bulk upsert filled a missing key with null | `NOT_NULL_WITH_DEFAULT` (read from the live schema) leaves such keys out; bulk upserts are grouped by key set | 6 unit tests incl. one upsert per key set |
| 3 | both delivered orders in 60 days: status paid, `payments` empty, `amount_paid` 0 | `portal_order_delivery('delivered')` marked paid but never recorded the payment | records what was still due as a payment by the rider (cash unless the bill says otherwise); none for credit / complimentary / already paid | live, in a transaction that always rolls back: 1,000 due → one payment of 1,000, `amount_paid` 1,000, `paid_at`, `delivered_at`, `dispatched_at` set |
| 4 | read from the function | two riders could both claim one delivery | the order row is locked while the claim is decided | live: a second claim → `already_claimed` |
| 5 | read from the function | `portal_upsert_order` replaced the whole document, wiping a payment / the kitchen status / the rider assigned meanwhile | the fields other devices own are kept; a paid or voided bill stays so | live: after the Order Taker's save the items were updated, kitchen status stayed `cooking`, the payment stayed, status stayed `paid` |
| 6 | 5 × `401` on `get_workspace_code` | my own S-1 change (an empty `200` became a `401` for a session-less browser) | none needed — every caller ignores the error | call sites read |

Not changed on purpose: the typed `delivery_status` / `kitchen_status` columns are never written by the till (0 of 3,429 orders), so the customer push notifications that read them never fire. That is a missing feature, not a data mismatch (every reader falls back to the document); switching it on would start notifications nobody has tested.
Left alone: 6 `403` RLS refusals on `customers` — a record carried over from another restaurant in the same browser, already set aside by the existing Data Integrity handling; one `555` from the gateway.

## 2. S-4 / S-5 — live
In a transaction that always rolls back: five wrong PINs → five identical replies, attempts 5, lock 15 min; the right PIN while locked → the same reply; 10 wrong → lock 1 h; right PIN after the lock → in; unknown number and blocked customer → the same reply; 30 codes in the hour → the 31st refused. Nothing left behind (0 test customers, 0 test codes).

## 3. Custom Website without a web server, and the Super Admin view
Five database functions (`custom_site_status / _save / _rotate_key / _revoke_key`, `sa_custom_site_overview`). Live, rolled back: status, save (a scheme-less address gets https and a trailing slash is dropped; http, credentials, a bare host and a wrong mode are refused), key format `dtcs_` + 43 characters, **no secret in any read**, revoke, a rider is refused, a non-Super-Admin is refused the overview. The card uses them directly; only "Check connection" still needs the online server and says so. Super Admin → Monitoring lists every restaurant that connects its own site with a state (Delivering / Nothing for 3 days / Has a problem / No key yet). Screenshot: `docs/audit/2026-11-06-superadmin-own-websites.png`.
