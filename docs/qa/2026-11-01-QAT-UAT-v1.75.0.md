Written 2026-11-01. Everything marked **EXECUTED** was run by me in this session and the result is the real one. Everything marked **NOT EXECUTED** needs a device, a network or a person I do not have; it is listed so nothing is assumed.

## 2. Scope of this release (the test items)
1. **All Categories grid** — the 4-box button beside "All" in the POS (top ribbon and side panel), with the picker dialog, item counts, full-name wrapping (ported from the offline POS v1.21.0).
2. **Order tracking, one definition** — `trackingView()`, `OrderTrackingPanel`, `OrderTrackingDialog`; the customer's `#/track` page now draws the shared panel; the Delivery Board has a *Live tracking* button; the Delivery Board and Live Riders map follow the store.
3. **Rider app** — "Your location is OFF" reminder; Live switched on at a first claim for a rider who never chose.
4. **Design package** — customer app parked, Order Taker app designed (no application code).

Not in scope of this release: the Windows/Web shell re-skin (sidebar, top bar, dashboard), invoice numbering (B4), security S2–S6, PRA, any database change.

## 6. Defect log
| ID | Severity | Found | Status |
|---|---|---|---|
| D-1 | **High** | The Delivery Board read the orders once and only again after its own actions, so a status or position set on a rider's phone, or a new customer order, did not show until something on the board was touched (the 8-second poll is switched off by `ENABLE_REDUNDANT_ORDER_POLL = false`). | **FIXED** — follows `onDataChange('orders')`; pinned by test |
| D-2 | Medium | The Live Riders map had the same defect: a rider's new position did not move the pin. | **FIXED** — same |
| D-3 | Medium | The customer's tracking page showed "Order Placed" while the restaurant had the order at *Cooking* on the Delivery Board (only the kitchen screen's status moved the step). The signed-in tracker already treated it as cooking. | **FIXED** — `cooking` counts as Kitchen Cooking; `rider_assigned` deliberately does not mean ready (a rider may take an order that is still cooking) |
| D-4 | Medium | Riders had to switch Go Live on by hand, so a customer rarely saw a rider moving (12 of 1,352 rider-assigned orders have a stored position). Also, only ~27 delivery orders carry a customer pin: most delivery orders are typed in by staff from phone calls, not placed on the website, so there is no map for them. | **MITIGATED** — reminder banner, Live on at a first claim. **Not a bug to fix:** phone orders cannot be tracked by the customer unless a location is captured |
| D-5 | **Medium** | A portal rider's GPS ping is saved with `portal_upsert_order`, which replaces the order's whole `data` with the rider phone's copy. A stale copy can overwrite a newer kitchen or status change made on the server. | **OPEN** — fix is a small dedicated function `portal_rider_ping(token, order, lat, lng)` that merges only the position. It changes the production database: **needs your approval and a confirmed backup** |
| D-6 | Low | `CategoryGridDialog` used the global `JSX` type, which React 19 no longer provides (TypeScript error). | **FIXED** — `ReactNode` |
| D-7 | Low | `TrackOrderPage` kept now-unused imports after the refactor. | **FIXED** |
