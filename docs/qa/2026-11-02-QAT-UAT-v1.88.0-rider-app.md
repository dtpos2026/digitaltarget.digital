# QAT and UAT — DT POS Enterprise v1.88.0 (DT Rider: the design package's rider screens)

Design package build order, **step 4 (phone apps inner screens)**, first part: the Rider app (`design-project/05-rider-app`). Step 3 (customer website) is still waiting for the database backup confirmation, so step 4 went first.

## 1. What was built
The rider app (`#/rider-portal`, the DT Rider Android app; also `/rider` inside the till) now looks and works like the design: rider orange on the DT neutrals, large type, and every main action at least 52 px high near the bottom of the screen.

- **Four tabs: Home · Orders · Record · Profile.**
  - **Home (RID-04):**
    - The rider, their restaurant and branch, and the **Live** switch.
    - Three tiles: Active, Done today, Bills today.
    - My active orders, then orders waiting to be claimed, then Refresh.
  - **Orders (RID-05, RID-17):** Mine · Available · History.
  - **Record (RID-16):** Today / This week / This month, the total, a bar per hour or day, and the delivered orders.
  - **Profile (RID-18):**
    - Live location switch and a dark theme for night shifts (RID-22, remembered on the phone).
    - Help and support, the rider's photo and name card, and Log out, which asks first.
- **Claim (RID-08):** one confirmation sheet showing the address, distance, what to collect and the kitchen's state.
- **Ready alert (RID-06):** a banner with **Claim** (or **Open** if it is already the rider's) and **Later**, and a short vibration. It replaces the 10-second toast.
- **One delivery, start to finish.** Each screen has one big button for the next step:
  1. **Pickup (RID-09):** map to the restaurant, the branch with a call button, and **Navigate to restaurant**. It also shows the kitchen's state, for example "Food is ready — collect it".
  2. **Confirm pickup (RID-10):** tick each item in the bag. **Confirm pickup** stays locked until every item is ticked. The ticks are not stored.
  3. **Start the ride → I have reached (RID-11):** a four-step tracker (Picked up · On the way · Reached · Delivered), the map, the customer's address, Navigate, Call and Help.
  4. **Hand over (RID-13):** the amount to collect, in large type, and how the bill is settled:
     - **Cash on delivery** (or card / online, with its account);
     - **Paid already**, for a bill paid before it left;
     - **Balance after advance**;
     - **On account (credit)**.

     When money is owed, **Delivered** stays locked until the rider ticks "I collected the full amount".
  5. **Delivered (RID-15):** the order done, today's count and today's bill total, and Back to orders.
- **Other screens:**
  - **Call (RID-12):** a sheet with Call and **Send tracking link on WhatsApp** (the same tracking link as before).
  - **Change status (⋯):** corrects a wrong tap. Choosing Delivered still goes through the money screen.
  - **Help (RID-19):** four common problems. Each opens WhatsApp to the restaurant with the order number, customer and address already written. There is also a Call restaurant button.
  - **States (RID-21):** banners for offline, location off or blocked, a failed record (with Retry), and a cancelled order. Lists show placeholder rows while loading, and empty lists show one sentence and one action.
- **Sign in (RID-02):** the same sign-in, now in the rider look. A wrong PIN, a missing field, or a lockout message from the server now shows **on the screen**, not only in a toast.

### Kept exactly as it was
All the logic stays in `src/pages/RiderAppPage.tsx`, and the existing tests that guard it pass unchanged:
- Sign-in through the portal; the 15-second poll and the Refresh button go to the server.
- The heartbeat goes through the portal, not a blocked write.
- GPS writes are limited to one every 15 s / 20 m per order.
- **Claim and every stage change go to the server first.** A refusal is shown, and the order does not move on the phone.
- Delivered marks the bill paid, and the customer is notified at each stage.
- Log out ends the portal session.

## 2. Things the screens now say honestly (and decisions for the owner)
1. **"Earnings" is the total of the bills the rider delivered, not the rider's pay.** The server's figure (`portal_my_history`) adds up `grandTotal`, and the system has no rider fee or commission. So the tab is called **Record**, the figure is **"Bills delivered"**, and the screen says *"Your pay is agreed with your restaurant."* The profile card's tile is now **"Bills Rs"**.
   - **Decision:** should DT Rider pay riders per delivery (a fixed fee, a % of the bill, or the order's delivery charge)? That needs a setting and a small server change; then the app can show real earnings.
2. **Cash collected is not recorded.** "I collected the full amount" is a check on the phone. The server records only the delivery and marks the bill paid (as before). A cash hand-over / rider settlement step is a backend addition.
3. **Found while building, not changed:** a delivery bill with an **advance** (part paid before it left) is marked paid on delivery, but its *amount paid* stays at the advance. Reports then count only the advance as money taken. The fix is server-side (`portal_order_delivery` should set the amount paid to the bill total on delivery), so it needs your approval before the database function is changed.
4. **The restaurant's phone on a rider's phone.** `portal_restaurant` does not return the restaurant's number. So on a DT Rider phone, **Call restaurant** works only when the branch or restaurant number is on that phone, and **WhatsApp** opens WhatsApp with the message written so the rider picks the restaurant's chat. Returning the phone from `portal_restaurant` is a small additive change. **Your approval is needed.**
5. **Not built (need a backend):** RID-03 code sign-in, RID-14 proof of delivery, RID-20 notifications, and an alert when the app is **closed** (RID-06 works only while it is open). These are listed in the build order's step 6.
